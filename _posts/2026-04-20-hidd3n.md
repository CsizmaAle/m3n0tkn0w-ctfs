## **Recognition Pattern**
- "Search for the unsearchable" → a plain string search won't find it; it's encoded or hidden in protocol fields
- Gibberish strings showing up as test/query names → looks like exfiltration, probably Base64
- Low-traffic pcap → I can go through it by hand and pick out the odd ones
- Strings ending in `=`, or only alphanumeric plus `+`/`/` → Base64, so concatenate them and decode

## **Approach and Methodology**
### **Initial Analysis**
Ran `binwalk` and `cat` to check for hidden messages, then opened the file in Wireshark.  

### **Steps Taken**
Opened the file in Wireshark (`wireshark challenge.pcap`). There isn't a lot of traffic, so I went through it manually and found the context: some tests being run. A few of the test names were gibberish and weren't recognized by the platform/device running them. So I copied the test names into a notepad file:

```
VVZUSUNT
e2Ruc19u
NG1lZWVl
M3NfY2Fu
X2wzNGtf
ZEF0YX0
```

I went to dcode → cipher identifier. After adding the ciphertext, it recommended Base64.  

![dcode identifying the strings as Base64](Hidd3n_1.png)

## **Solution and Flag Retrieval**
*Final Exploit / Command Used:* concatenated the strings, entered them into dcode's Base64 decoder, and hit decode.  

## **Lessons Learned**
- When a plain search for the flag prefix comes back empty, the flag is encoded or split across protocol fields — I start looking for anomalies like weird hostnames or odd DNS queries.
- The flag itself (`dns_n4meeee3s_can_l34k_dAta`) basically explained the technique — DNS exfiltration, hiding data in query names because DNS traffic is rarely inspected.
- Typing `dns` in Wireshark's display filter narrowed the traffic down fast.
- The pieces individually looked like gibberish — the trick was concatenating the short Base64 strings first, then decoding the whole thing as one message.
